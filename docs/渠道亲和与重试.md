# 渠道亲和、重试与故障切换

lite-cpa 如何把会话钉在上游 API key 上、何时重试、中转站应如何切换。

## 为什么需要亲和

多 key / 多供应商能提高可用性，但 **prompt cache 和会话状态通常绑在单一上游凭证上**。同一 CLI 会话若在不同 key（或不同中转）之间乱跳，缓存命中率会掉，行为也可能不一致。

渠道亲和是一层 **成功记忆**：某次请求成功后，记住服务该会话身份的 `UpstreamKey`，下次优先用它。

它 **不是** 普通负载均衡。没有 pin、或 pin 被清掉 / 过期时，仍走优先级与轮询。

## 钉住的是什么

lite-cpa 只做 API-key 上游（无 OAuth 账号）。粘性值是：

```text
会话身份  →  UpstreamKey.ID   （如 laysath-0）
```

`UpstreamKey.ID` 形如 `{provider-name}-{index}`，不是单独的供应商展示名。

## 何时会粘住

### 1. 模型族要匹配

默认模型族（亲和开启且未写自定义 `rules`）：  
`claude`、`gpt`、`gemini`、`grok`、`glm`、`kimi`、`qwen`、`minimax`。

匹配方式是 **子串、不区分大小写**（`proxy-claude-x` 能命中 `claude`）。

### 2. 必须有会话身份

提取顺序：

1. **Session 请求头**（第一个非空）：  
   `Session-Id`、`session_id`、`X-Session-Id`、`Thread-Id` …
2. **协议 body**（没有 session 头时）：
   - 路径含 `/messages` → `metadata.user_id`，再试 `prompt_cache_key`
   - `/responses` 或 chat completions → `prompt_cache_key`，再试 `metadata.user_id`

两者都没有 → **不粘**，普通选 key。

### 3. 查缓存

```text
cacheKey ≈ "{规则名}:{亲和值}"  →  key ID
默认 TTL：600 秒（仅进程内存）
```

- **命中** → 优先试该 key（仍在该模型 key 池内）
- **未命中** → 按优先级 / 轮询
- **成功** → `Record` pin（switch-on-success：钉实际成功的那把）
- **失败** → `Clear` 该 cache key 的 pin

## 重试次数

由顶层 `request-retry` 控制：

```text
maxAttempts = min(1 + request-retry, 该模型可用 key 数)
```

例如 `request-retry: 2` 且有 5 把 key → 单次请求最多 **3** 次尝试。

可触发换 key 的上游结果：

- HTTP **401 / 403 / 429 / ≥500**
- 网络 / 传输错误

其它 4xx 直接回客户端，不轮转。

**同请求内没有按时间 backoff**，失败后立刻换下一把。

## 故障切换模式（按 provider 的 `name`）

可重试失败后，行为取决于 **失败那把 key 所属** 的供应商：

| `failover-mode` | 行为 | 适用 |
|---|---|---|
| `key`（默认） | 标记本 key 已试，换下一把未用 key（可能仍在同站） | 官方多 key、key 级限流 |
| `provider` | 本请求内跳过该 `name` 下 **全部 key** | 中转站（一站挂则 key 全废） |

```yaml
- name: openai-official
  failover-mode: key
  base-url: https://api.openai.com/v1
  ...

- name: laysath
  failover-mode: provider
  base-url: https://ai.laysath.cn/v1
  ...
```

多个供应商配置 **相同客户端 `alias`** 时，key 会 **合并** 成一个池；选路仍看 `priority` 与轮询。

## 亲和 × 重试 × 切换（单次请求）

```text
1. 查亲和 → 可选 preferred key
2. 循环（≤ maxAttempts）：
     优先 sticky，否则 Selector.Pick
       - 尽量同供应商
       - 跳过已标记死亡的供应商（provider 模式）
     调上游
     失败：
       若是 sticky key → Clear pin
       若 skip-retry 且用过 sticky → 停止
       若 failover-mode=provider → 跳过整个 name
       continue
     成功：
       Record pin → 返回
3. 返回最后错误
```

### 生产相关默认值

| 配置 | 默认 | 用意 |
|---|---|---|
| 亲和开启 | 默认开 | 利于会话缓存 |
| 亲和 TTL | **600s** | 避免长时间粘死中转 |
| 族规则 `skip-retry-on-failure` | **false** | 允许故障切换；成功再 pin |
| `switch-on-success` | true | 钉真正成功的 key |
| `failover-mode` | 未写则 `key` | 中转请显式 `provider` |

## 常见坑（「为什么还打旧渠道」）

1. **TTL 未到期** — pin 最多保留 600s（或你设的 `default-ttl-seconds`）。  
2. **自定义规则 `skip-retry-on-failure: true`** — sticky 失败后本请求不换。  
3. **中转仍用 `failover-mode: key`** — 会在同站换 key。应改为 `provider`。  
4. **新加了更高优先级供应商** — 已有 pin 仍优先旧 key，直到清除/过期。  
5. **请求没有身份字段** — 亲和根本不生效。  
6. **进程重启** — 内存缓存清空（无 Redis）。

当前 **没有** 管理端「清空亲和缓存」接口。实用手段是短 TTL、重启；失败路径已会 Clear 对应身份。

## 推荐配置

### 仅官方

```yaml
request-retry: 2
openai-responses:
  - name: openai-official
    failover-mode: key
    base-url: https://api.openai.com/v1
    api-key: sk-...
    models: [{ name: gpt-5, alias: gpt-5 }]
```

### 官方 + 中转（同 alias 合并池）

```yaml
request-retry: 3
openai-responses:
  - name: openai-official
    priority: 0
    failover-mode: key
    base-url: https://api.openai.com/v1
    api-key: sk-official
    models: [{ name: gpt-5, alias: gpt-5 }]

  - name: laysath
    priority: 1
    failover-mode: provider
    base-url: https://ai.laysath.cn/v1
    api-key-entries:
      - { api-key: sk-a }
      - { api-key: sk-b }
    models:
      - { name: gpt-5, alias: gpt-5 }
      - { name: grok-4.5, alias: grok-4.5 }
```

### 亲和开关

```yaml
channel-affinity: true                    # 或 [claude, gpt, grok]
# channel-affinity: false
```

## 调试

`debug: true` 时 stderr 会打 affinity hit / clear / record 与轮转日志。  
可选 request-log 会记供应商名与状态码，尚不包含亲和指纹字段。
