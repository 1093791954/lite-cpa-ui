# 格式转换是如何实现的

本文说明 lite-cpa 如何在三种协议之间做请求/响应转换。

## 1. 三种协议与内部名称

| 对外入口 | 配置上游 | 内部 Format |
|---|---|---|
| `POST /v1/chat/completions` | `openai-completions` | `openai`（chat） |
| `POST /v1/responses` | `openai-responses` | `openai-response` |
| `POST /v1/messages` | `anthropic-messages` | `claude` |

客户端格式由 **HTTP 路径** 决定；上游格式由 **配置里该 model 绑定的 provider** 决定。

```text
客户端协议 (from)  ──TranslateRequest──▶  上游协议 (to)
客户端协议 (from)  ◀─TranslateStream/NonStream──  上游协议 (to)
```

## 2. 总览：一次请求怎么走

```text
Client
  │  Bearer gateway api-key
  ▼
HTTP Handler  (/v1/chat/completions | /v1/responses | /v1/messages)
  │  读 body，解析 model / stream
  ▼
Selector  按 model 别名选上游 key（多 key 轮询 + 失败重试）
  │
  ▼
Executor.Execute(from=客户端格式, to=上游格式)
  │  1) TranslateRequest(from → to)
  │  2) 设置上游 model 字段
  │  3) HTTP 调上游
  │  4) TranslateNonStream / TranslateStream(to → from)
  ▼
写回客户端（JSON 或 SSE）
```

关键代码：

- 入口：`internal/server/server.go` → `handleProxy`
- 执行：`internal/executor/executor.go` → `Execute`
- 注册表：`internal/translator/registry.go` + `register.go`

## 3. 注册表：按 (from, to) 查转换函数

启动时 `translator.RegisterBuiltin()` 把所有边注册进内存 map：

```go
Register(from, to,
  requestTransform,                 // 请求：客户端 → 上游
  ResponseTransform{
    Stream:    ...,                 // 流式响应：上游 → 客户端
    NonStream: ...,                 // 非流式响应：上游 → 客户端
  },
)
```

查找规则：

| 阶段 | 查表方式 |
|---|---|
| 请求 | `requests[from][to](model, body, stream)` |
| 响应 | `responses[客户端from][上游to]` 里的 Stream/NonStream |

同格式（如 chat→chat）走 identity 转换：几乎透传，只规范化 `model` / `stream` 等字段。

## 4. 目录布局：`{from}/{to}`

跨格式转换放在：

```text
internal/translator/
  chat/claude/          # 客户端 chat → 上游 claude（请求）
  chat/responses/       # 客户端 chat → 上游 responses
  claude/chat/          # 客户端 claude → 上游 chat
  claude/responses/     # 客户端 claude → 上游 responses
  responses/chat/       # 客户端 responses → 上游 chat
  responses/claude/     # 客户端 responses → 上游 claude
  chat_identity_*.go    # chat → chat
  responses_identity.go # responses → responses
  common/sse.go         # SSE 拼装工具
  register.go           # 注册所有边
  registry.go           # 查表与调用
```

注意：

- **路径表示方向**，不是「两个名字随便放」。
- **请求**转换器在 `from/to` 包里。
- **响应**转换器往往在「对侧」包：因为响应要从上游格式变回客户端格式。  
  例如 chat 客户端打 claude 上游：
  - 请求：`chat/claude` 的 `ConvertOpenAIRequestToClaude`
  - 响应：`claude/chat` 的 `ConvertClaudeResponseToOpenAI`

`register.go` 把这些函数绑到同一条边上。

## 5. 完整转换矩阵

| 客户端 \ 上游 | chat (`openai`) | responses | claude |
|---|---|---|---|
| **chat** | identity | chat↔responses | chat↔claude |
| **responses** | responses↔chat | identity | responses↔claude |
| **claude** | claude↔chat | claude↔responses（含 hop） | 同格式透传 |

### 5.1 直接实现的边

| 边 | 请求函数 | 响应函数 |
|---|---|---|
| chat → claude | `ConvertOpenAIRequestToClaude` | `ConvertClaudeResponseToOpenAI` |
| claude → chat | `ConvertClaudeRequestToOpenAI` | `ConvertOpenAIResponseToClaude` |
| chat → responses | `ConvertOpenAIChatCompletionsRequestToOpenAIResponses` | `ConvertOpenAIResponsesResponseToOpenAIChatCompletions` |
| responses → chat | `ConvertOpenAIResponsesRequestToOpenAIChatCompletions` | `ConvertOpenAIChatCompletionsResponseToOpenAIResponses` |
| responses → claude | `ConvertOpenAIResponsesRequestToClaude` | `ConvertClaudeResponseToOpenAIResponses` |

### 5.2 两跳（hop）的边：claude → responses

没有单独手写一整套 Claude↔Responses 时，**请求**走两跳：

```text
Claude 请求
  ──Claude→Chat──▶  Chat 请求
  ──Chat→Responses──▶  Responses 请求
```

**响应**也走两跳，且**维护两份独立状态**（不能共用一个 param）：

```text
Responses SSE
  ──Responses→Chat──▶  Chat chunk（状态 bag A）
  ──Chat→Claude──▶  Claude SSE（状态 bag B）
```

对应：

- 请求 hop：`claude/responses/request.go`
- 响应 hop：`responses/claude/response.go`（`hopState{Chat, Cla}`）

## 6. 请求转换在做什么

转换器统一签名：

```go
func(model string, rawJSON []byte, stream bool) []byte
```

实现特点：

1. **不反序列化成大 struct**：主要用 `gjson` 读字段、`sjson` 写字段，减少分配。
2. **以目标协议的 JSON 骨架为底**，再把源协议字段填进去。
3. 处理常见映射，例如：

| 概念 | chat | responses | claude |
|---|---|---|---|
| 对话内容 | `messages[]` | `input` / `instructions` | `messages[]` + `system` |
| 工具 | `tools[].function` | `tools[]`（扁平 name/parameters） | `tools[].input_schema` |
| 工具调用 | `tool_calls` | `function_call` / `function_call_output` | `tool_use` / `tool_result` |
| 长度限制 | `max_tokens` | `max_output_tokens` | `max_tokens` |
| 推理 | `reasoning_effort` 等 | `reasoning.effort` | `thinking` |

4. 最后 executor 会再写一次上游真实 `model` 名（别名 → 配置里的 `models[].name`）。

## 7. 响应转换：非流式 vs 流式

### 7.1 非流式

```go
TranslateNonStream(ctx, upstreamTo, clientFrom, model, originalReq, translatedReq, body, &param)
```

- 上游返回完整 JSON（或 Claude 跨格式时上游可能是 SSE 聚合后再 NonStream）。
- 转成客户端期望的一个 JSON 对象（如 `chat.completion` / `response` / Claude `message`）。

Claude 特殊点：跨格式非流式客户端时，executor 仍可能对 Anthropic 使用 `stream=true`，因为部分 NonStream 转换器按 **SSE `data:` 行** 聚合；聚合后返回**完整 JSON**，而不是把最后一块 `[DONE]` 当 body。

### 7.2 流式

```text
上游 SSE 行
  → TranslateStream(...) 得到 0..N 个客户端 chunk
  → frameForClient 统一成合法 SSE 帧
  → Flush 给客户端
```

规则：

| 客户端 | 帧格式 |
|---|---|
| chat | 每块 `data: {...}\n\n`，结束常有 `data: [DONE]\n\n` |
| responses / claude | 多行事件：`event: ...\ndata: ...\n\n` |

**同格式**流式：直接透传上游 SSE（`streamPassthrough`），避免把 `event:` / `data:` 拆成两个独立事件。

**跨格式**流式：逐行（或按转换器输出块）翻译，再用 `frameForClient` 补全分隔符。

转换器内部常用 **param 状态机**（`*any`）：跨 chunk 累积 tool call 参数、文本缓冲、sequence number 等。

## 8. 模型路由如何接到转换

1. 配置里每个上游声明 `models[].name`（上游真名）与 `alias`（客户端可见名）。
2. `pool.BuildRegistry` 把 alias → 一组 `UpstreamKey`（含 provider 类型、base-url、headers、多 key）。
3. 请求里的 `model` 用 alias 解析；找不到则去掉 thinking 后缀 `model(high)` 再试。
4. Executor 的 `from` = 客户端 Format，`to` = key.Provider 对应 Format。

因此：**格式转换与「选哪家上游」解耦**——先选 key，再按 (from,to) 查转换器。

## 9. 实现时注意点

1. **不要把 Codex 私有路径当成标准 Responses**  
   lite-cpa 的 responses 是标准 `POST {base}/responses`，不是 ChatGPT Codex backend。

2. **hop 必须双状态**  
   Responses→Chat 与 Chat→Claude 各自有流式状态，合并成一个 param 会丢 tool/文本边界。

3. **SSE 分隔符**  
   `event:` 与对应 `data:` 必须在同一事件里，用 `\n\n` 结束事件，不能每行各加一个 `\n\n`。

4. **低内存**  
   请求只做一次 `TranslateRequest`；流式不落完整响应 body；scanner 缓冲有上限。

5. **JSON 库选择**  
   热路径用 gjson/sjson；避免整包 `encoding/json` 反复 marshal。

## 10. 想改/加一种映射时怎么做

1. 在 `internal/translator/{from}/{to}/` 增加或修改 `request.go` / `response.go`。
2. 在 `register.go` 绑到对应 `Register(from, to, ...)`。
3. 补 E2E：同格式透传 + 跨格式非流式 + 跨格式流式（检查 `event:`/`data:` 与终止事件）。
4. `go test ./...`
